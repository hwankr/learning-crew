## 1. [중대] perEntry 8개 상태의 9번째 선택/추가 — 고침

**한 일.** 새 순수 함수 `hasTagRoom(cur, t)`를 두고, 피커의 세 입구가 전부 이걸 지난다:
칩 토글(`toggleTag`), `+ 추가` 칩 열기, 인라인 입력 확정(`addTag`). 자리가 없으면 아무것도
바꾸지 않고 칩 아래 잔글씨로 이유만 말한다 — **"태그는 8개까지예요. 하나 빼면 다시 고를 수
있어요."** (`.tag-hint.warn`, 시트의 `draft-note warn`과 같은 붉은 잔글씨).

`hasTagRoom`의 뜻:
- 끄기·이미 켜진 태그 → 자리를 새로 먹지 않으므로 통과. **꽉 찬 상태에서도 끄는 건 늘 된다.**
- `'OFF'` → 나머지를 전부 비우고 혼자 남으므로 통과. 꽉 차도 "쉬는 날"로 갈 길은 열려 있다.
- 정화되지 않는 이름(빈 문자열·12자 초과) → 통과. 한도 문구가 진짜 실패 사유(공용 검증의
  "12자 이하로 적어 주세요")를 가리면 안 되므로, 그건 `onAddCustomTag`가 말하게 둔다.

**보이는 것.** 지금 켤 수 없는 칩은 `aria-disabled` + `.tag-chip.limit`(opacity 0.5)로 흐려
둔다. `disabled`로 빼지 않은 이유: 탭 순서에서 사라지면 "왜 안 되는지" 물어볼 자리조차
없어진다. 눌러 본 뒤에 이유를 말하는 건 저장 버튼(`aria-disabled` + `tried`)과 같은 규칙이다
— 여덟 개를 고른 것 자체는 잘못이 아니라 다 채운 것뿐이라, 가만히 있는 사람에게 붉은 줄을
띄우지 않는다.

**`+ 추가` 칩의 예외 하나.** 입력이 이미 열려 있으면 한도와 무관하게 닫는 동작은 늘 된다.
(입력을 열어 둔 채 여덟 번째 태그를 골랐다고 열어 놓은 칸을 닫지도 못하면 갇힌다.)
여는 쪽만 막는다. `addTag`에도 같은 검사를 한 번 더 둔 이유가 이 순서다 — 입력을 연 **뒤에**
자리가 없어질 수 있다.

**normalizeTags의 절단은 그대로 뒀다** — 경계 방어로 남기되 UI가 거기 기대지 않는다.
회귀 테스트가 절단의 실제 결과를 그대로 박아 두었다: 꽉 찬 기록에 `'하하'`를 넣으면 잘려 나가
(눌러도 안 켜짐) `'AA'`를 넣으면 `'dd'`가 조용히 밀려난다. 그래서 막는다는 뜻이다.

## 2. [중대] 접기 기준이 개수뿐 — 고침 (개수 → 어림 폭)

`PICKER_COLLAPSED = 8` (개수)을 버리고, **칩 폭을 어림해 실제 줄바꿈을 흉내 내는** 판정으로
바꿨다. 줄 수를 정하는 건 칩 개수가 아니라 이름 길이이기 때문이다.

- `chipWidth(name)` — 스타일시트에 박힌 값에서 계산: 13px/700, 좌우 패딩 14px, 테두리 1.5px
  둘. 한글·한자·가나·전각·이모지는 글자당 13px, 라틴·숫자·기호는 0.58배.
- `chipRows(widths)` — flex-wrap과 같은 탐욕 규칙으로 줄 수를 센다(gap 6px).
- 기준 폭 `PICKER_WIDTH = 350` — **390px 화면의 시트 안쪽**(패딩 20px 둘). 데스크톱 시트
  (460px → 안쪽 408px)는 더 넓어서 여기 기준이면 조금 일찍 접히지만, 좁은 쪽을 기준으로
  잡아야 "대략 두 줄" 계약이 정작 좁은 화면에서 깨지지 않는다.
- `collapsible` = 전체 + `+ 추가` 칩이 두 줄에 안 들어갈 때. 접을 땐 **선택된 태그를 먼저
  고정**하고, 앞에서부터 한 개씩 넣어 보다가 `+n` · `+ 추가`까지 합쳐 두 줄을 넘기는 첫 칩에서
  멈춘다. (넘치는 칩만 건너뛰면 목록이 원래 순서와 다른 자리에서 끊겨 어디까지 보고 있는지가
  흐려진다.)

DOM 측정은 여전히 안 한다 — 시트가 열릴 때마다 관측을 붙이지 않고, 순수 함수라 그대로
테스트된다. 옛 `+1 여유` 규칙은 필요 없어져 지웠다: 판정이 줄 단위라 한 개를 감추는 건 그게
실제로 한 줄을 줄일 때만 일어난다.

**실측 대조** (실제 컴포넌트를 `renderToStaticMarkup`으로 뽑아 390px 프레임에 넣고 헤드리스
Chrome으로 `offsetTop` 기준 줄 수를 셈):

| 경우 | 실측 줄 | 결과 |
|---|---|---|
| 커스텀 없음 | 2 | 안 접힘 |
| 짧은 한글 커스텀 4개 | 2 | `+2` |
| 짧은 한글 커스텀 5개 | 2 | `+3` |
| **12자 이름 2개** | **2** | `+2` — 옛 기준(칩 9개 초과)에선 접히지 않아 4줄이던 자리 |
| 12자 3개 + 맨 뒤 선택 | 2 | `+3`, 선택된 12자 태그가 남음 |
| 영문 커스텀 5개 | 2 | `+3` |
| 태그 8개 꽉 참(한글) | **3** | 아래 참고 |

어림 폭 대 실측 폭: 자격증 70/69 · 코딩테스트 96/95 · OFF 53.6/54 · 12자 한글 187/186 ·
`+ 추가` 73/72. 라틴과 `+n`은 조금 넉넉하게(보수적으로) 잡힌다.

**한 경우만 3줄이다** — 태그를 여덟 개 고른 상태. 선택된 태그는 접혀도 반드시 보인다는
계약과 두 줄 계약이 부딪히는 지점이고, 코드 주석대로 **선택을 살렸다**. 여덟 개를 고르는 건
한도 끝이고, 그 상태에선 `+ 추가`도 어차피 흐려져 있다.

## 3. [권고] 인라인 입력의 DOM maxLength — 고침

`maxLength={TAG_LIMITS.nameLen}` → `{TAG_LIMITS.nameLen * 2}` (24). DOM maxLength는 UTF-16
code unit을, 공용 검증은 코드포인트를 센다. 코드포인트 하나가 최대 두 unit이므로 두 배로
열어 두면 규칙보다 좁아지는 일이 없고, 이모지 7~12자 이름이 입력 단계에서 잘리지 않는다.
안내·판정은 그대로 `onAddCustomTag`(공용 sanitize) 한 곳에서만 나온다.

## 리뷰 포인트

- `PICKER_WIDTH = 350`은 **모바일 기준 상수**다. 데스크톱 시트(408px)에서는 한두 칩 일찍
  접힌다 — 펼치면 그만이라 좁은 쪽을 지켰다. 반응형으로 하려면 관측(ResizeObserver)이
  필요하고, 그건 이번에 일부러 피한 길이다.
- 태그 8개를 고른 상태에선 `+n` 뒤로 `OFF`가 숨을 수 있다. 그 상태에서도 선택된 태그를 끄는
  건 늘 되고 `+n`으로 펼치면 OFF가 나온다.
- 어림 폭은 기본 시스템 폰트 기준이다. 폰트가 크게 바뀌면 `CHIP_FONT`/`NARROW`를 같이 봐야
  한다(주석에 근거를 적어 뒀다).
